# Optiquity Content Pipeline — Manual

## What it is

The Optiquity Content Pipeline is an open-source **framework** for turning your own repositories into targeted content — documentation and marketing alike — that stays tied to a source of truth. It is a control plane: **content-free by design**, it ships the machinery and generic defaults while you supply the audiences, platforms, formats, and workspaces. Its mission document frames it as a repo-grounded, extensible, two-stage pipeline — ideation (repo + audience → ranked idea queue) and generation (idea → formatted artifact) — running on Claude Code CLI, grounded in read-only Graphify knowledge graphs of source repos. Grounding is the core idea: Graphify turns any folder (code/docs/scripts/PDF/images) into a queryable knowledge graph, and the pipeline reads that graph to back every claim it makes.

The read-only boundary is firm. The pipeline reads source graphs (by file path, MCP query, or pre-exported wiki) and only ever writes inside optiquity-content-pipeline/. Client repositories stay untouched — each one is checked out locally, and its graph is built in place, where the graphify-out/ is gitignored inside the client repo, so it never dirties it.

Drafts themselves are generated by a chain of Claude Code agents — a **researcher → writer → reviewer** — the product-plane layer that produces and checks each piece within the same CLI.

For this manual the bound sources are the pipeline's own tree: its design record and its Python engine. It is written for the person standing the project up and keeping it running — what the design calls the Primary author (solo/small-team).

## Two ways to run it

Before the concepts, it helps to know how you would actually run the framework. There are two operating models — both covered in `docs/operating-model.md`, both with a QuickStart section.

- **Solo.** Clone the repo, add a workspace, and run it on your own repos. This is the fastest path; `quickstart.md` §A walks it end to end. (Your own repo is a client too — by convention you are `workspaces/self`.)
- **Framework + private instances.** You maintain this public framework repo, and each user — including you — keeps a *private instance* that pulls your framework improvements non-destructively via `scripts/update-from-upstream.sh`. Because framework files and instance content never share a file, those updates merge cleanly and leave your content untouched, while the public repo stays content-free (enforced in CI, not by willpower). `quickstart.md` §B covers the maintainer setup.

Your own instance is simply the first private instance; others clone the public repo to make their own. Either way there is only ever one pipeline repo with many workspaces — never a separate repo per client.

## Durable rules

Five invariants hold across every session and every instance, and the rest of this manual assumes them. They are stated in full in `CLAUDE.md` and elaborated throughout the glossary below — this is the short authoritative summary.

1. **Read-only, always.** Source and client repos are never written, edited, moved, or committed to. The pipeline only reads a client's Graphify graph by path.
2. **A workspace per client — never a repo per client.** Each client repo gets one `workspaces/<client>/` directory; there is one pipeline repo with many workspaces, and one client's content can never leak into another's.
3. **The tracking spreadsheet is the single source of truth** for status and progress. `state.md` is a derived mirror of it — if they disagree, the spreadsheet wins and `state.md` is updated to match, never the reverse.
4. **The public framework repo stays empty of client content.** Generic `provenance: framework` defaults are welcome (they are the deliverable); an instance profile, any `provenance: instance` entry, and real client workspaces never appear there.
5. **Instances extend by adding files; they never edit framework files.** Downstream adds populated registries, workspaces, and a profile; framework improvements come from upstream, so updates stay conflict-free.

## Core concepts

With that operating model and those rules in mind, four ideas carry most of the system.

**The matrix.** Content is fanned out across a grid of topics × personas × platforms × formats. Each axis is a directory of entry files, so a new axis/stage is a config addition plus its own registry directory, not a rewrite. The first delivery phase stands up the four registries populated that these axes read from.

**Two stages — compose, then render.** v1 exposes exactly two waves: wave 0 = compose, keyed by artifact-id... wave 1 = render, keyed by deliverable-id. Compose builds one platform-neutral artifact from grounded facts; render fits and serializes that artifact into concrete output files.

**Tiered grounding.** Each fact carries a confidence tier, and the publish floor is a framework invariant — Only EXTRACTED-tier facts are published as fact; INFERRED/AMBIGUOUS are leads to verify — no run or override can relax it.

**Content-addressed identity.** An artifact's identity is a hash of its inputs, not a name someone assigns. The engine assembles those inputs with build_artifact_preimage and derives the id from them with mint_artifact_id; a preimage_check verifies a stored id against its recorded preimage. Because identity follows inputs, an unchanged run reproduces the same id. An authored outline can extend the preimage and is omit-when-absent: no outline → the key is absent, so artifacts without one keep their ids unchanged.

## Glossary

This glossary is self-contained: a new reader needs nothing else to understand the system's vocabulary. Terms are grouped by the part of the design they belong to, and each entry says what the thing is, where it sits in the pipeline, and how it relates to its neighbors.

### The matrix and its parts

- **The matrix.** The system's core data model: content is organized along nine orthogonal design axes and produced by fanning a request out across them. Five axes shape substance — Topic, Persona, Format, Voice, Goal — and four package and route the finished piece — Platform, Language, Output-type, Presentation. A request selects one or more values on each axis; the system resolves them and produces one concrete piece of content per combination. The matrix is what makes the system extensible: because every axis is just a directory of files, growing the matrix means adding files, never rewriting code.
- **Dimension (axis).** One of the nine axes of the matrix; "dimension" and "axis" mean the same thing here. Each dimension is characterized by four fixed facets rather than by an ad-hoc type: its role (content or rendering), its representation (a directory of preset entries, a set of tunable sliders, or a plain parameter), its cardinality (one value per piece, or a whole set), and whether it projects values onto other dimensions. Content dimensions decide what a piece says; rendering dimensions decide how one finished piece is packaged and delivered.
- **Facet.** One of the four properties that classify a dimension: role (content vs rendering), representation (discrete registry vs parametric sliders vs plain scalar parameter), cardinality (single vs set), and override-projection (whether the dimension's entries push values onto other dimensions). Adding a new dimension means choosing one value for each facet — never inventing a new kind of dimension. The facets are why the nine axes behave predictably and why a tenth could be added without special-casing.
- **Registry.** The directory that holds all the entries for one dimension — or for one of the other file-based collections such as content-kinds, render-targets, folio-types, or recipes. One registry is one directory; one file in it is one selectable value. Registries are what turn "add a value" into "drop in a file."
- **Entry.** One whole, populated value of a dimension, living in exactly one file — for example the `hiring-manager` persona or the `business` voice. An entry's identity is its filename: the frontmatter `id`, the filename slug, and the value you select are all the same string. An entry is the unit you *select*; the fields inside it are the units you tune.
- **Attribute.** One named, schema-declared field inside an entry — for example a persona's `knowledge_level`, or a voice's `formality` slider. Attributes are what you *bind or override* at fine grain, as opposed to entries, which you select whole. Every attribute has a declared type and a default value.
- **Schema.** The `_schema.yaml` file that sits inside each registry directory and declares that collection's attributes — each attribute's type, its default, its prose definition, and version stamps. The schema is what makes a registry safe to grow: it validates every entry and pins down what each field means. It is co-located with the entries it governs, one schema per collection.
- **Value vs. floor (schema default).** Every attribute has a schema default — the "floor" value it takes when nothing else sets it. An effective *value* is what the attribute actually resolves to for a given piece after all configuration is applied. The distinction is load-bearing for identity: only attributes whose effective value differs from the floor are recorded in a piece's identity, so shipping a new attribute at its default changes nothing that already exists.
- **One-file-add.** The framework's core extensibility promise and acceptance test: adding any value — a new topic, persona, platform, recipe, source, anything — must be exactly one new file in the right directory, conforming to that directory's schema. No index to update, no code to touch, no second edit. If an addition ever needs a second edit, that is treated as a defect to fix in the framework, not a step to document.
- **Provenance.** A metadata tag on every entry recording *who authored it* — `framework` (shipped as a generic default) or `instance` (added by a specific deployment). Provenance is independent of where the entry lives: framework defaults and instance additions can sit side by side in the same directory, told apart only by the tag. The rule attached to it is extend-don't-edit — an instance never edits a `framework` entry in place, it adds its own.
- **Scope.** Where an entry *applies*, encoded by its location rather than by a tag. An entry in a shared top-level registry directory is global; the same kind of entry under `workspaces/<client>/` applies to that client only. Scope is how one client's content is kept structurally isolated from another's, and how a universal template and a client-specific override coexist without a special mechanism.

### The value cascade

- **The cascade (value cascade).** The layered resolution that decides, for one piece of content, the final value of every attribute. Configuration can be set at several scopes — the schema floor, the entry itself, an instance-wide default, a per-client default, a recipe, and an ephemeral run — and the cascade folds them together under one rule: the most local, most specific, most immediate setting wins. It is what lets a global baseline exist while still allowing a single recipe or a single run to override any detail.
- **Rung (L0–L6).** One layer of the cascade. Six rungs are active, applied lowest to highest: **L0 schema-default** (the framework floor from the schema), **L1 entry-default** (the resolved entry's own values), **L2 global-default** (instance-wide, and mandatory for Voice, Language, and Output-type), **L3 workspace-default** (per client, optional), **L5 recipe** (per artifact), and **L6 run** (the ephemeral session, which is also the override layer). A higher rung overrides a lower one only for the attributes it actually sets. L4 is retired — it was a folio scope the design deliberately removed — and the remaining rungs are not renumbered, so rung citations stay stable.
- **The three mechanisms (M1 / M2 / M3).** "Precedence" in this system is really three separate mechanisms, all obeying most-local-wins but acting on different things at different times. **M1 (entry resolution)** decides, at load time, which definition of an entry wins when several layers redefine the same id, merging field by field. **M2 (value binding)** is the value cascade above: it binds each attribute's final value across the rungs — content dimensions bind at compose, rendering dimensions at render. **M3 (source selection)** runs earlier, at grounding time, over the source pool and the facts rather than over attribute values. Keeping them distinct is deliberate; collapsing them reintroduces ambiguity.
- **Configured value / scope default.** An attribute value carried at a *persistent* scope — a global default, a per-client (workspace) default, or a recipe setting. These are the ordinary way instances shape output. They are explicitly *not* called overrides: that word is reserved for the ephemeral run layer only.
- **Override.** A strictly reserved term: an *ephemeral, run/session-layer* value binding — collected when a session begins, applied during value binding, captured in the piece's identity, and never persisted. An override can bind a value but can never redefine an entry, because redefinition is a persistent authoring act. Persistent-scope settings are configured values, not overrides.
- **Combine operator.** The inline syntax that says how two settings for the same attribute merge when both are active. The defaults are type-driven: most-local-wins (replace) for scalars and prose, key-wise merge for maps, replace for ordered lists, and replace for sets unless a union is explicitly requested. The operator is one token on a single assignment — never itself a value that cascades — so combination stays predictable and cannot spiral.

### Content dimensions (what a piece says)

- **Topic.** The content dimension for *what a piece is about, and why it matters*. It owns the subject matter — grounded in the source, named by the entry's prose — plus the editorial significance: why this subject is worth saying now, and to whom. It deliberately owns nothing else: not the audience, not the structure, not the destination, not the persuasion objective. Topic binds during compose and is part of the artifact's identity.
- **Persona.** The content dimension for *who a piece is for*. It owns audience facts only — the reader's role and relationship to the subject, what they already know, what motivates them, their likely objections, and what makes a source credible to them. It owns no tone or register (that is Voice), but it does provide one cross-dimension value — a default voice for the reader, which the Voice dimension consumes. Persona binds during compose and is part of the artifact's identity.
- **Format.** The content dimension for *what shape or genre a piece takes* — a short opinion post, a long-form essay, a README. Formats are platform-agnostic: a Format carries no list of "valid platforms," because pairing a genre with a destination is the user's choice, not a rule the format enforces. A Format may declare named `parts` (ordered sub-outputs of one genre, like a slide deck's slides and presenter notes) and a section contract describing what a well-formed instance of the genre looks like. Format shapes the intermediate representation's structure, binds during compose, and is part of the artifact's identity.
- **Voice.** The content dimension for *how a piece sounds* — formality, humor, warmth, energy, narrator persona, plus free-text guidelines. It is parametric: a named voice is a saved configuration of sliders plus guidance, and those sliders are tunable per recipe or per run. Voice owns all register and affect; it never owns didactic function or reading level, which belong to Persona and Format. It is one of the three dimensions an instance must give a global default for, and it binds during compose as part of the artifact's identity.
- **Goal.** The content dimension for *what outcome a piece drives* — to explain, to convince, to prompt a specific reader action. It is the one *set-valued* dimension: a single piece can serve a whole set of goals at once, and selecting several goals stacks them into one artifact rather than fanning out into several. Each goal is tagged strategic or action (a call-to-action is simply a goal of kind action). The goal-set is sorted and de-duplicated into the artifact's identity, and goals may also nudge which sources are preferred at grounding time.
- **Lexicon (not a dimension).** A content-side registry carrying *house style* — preferred and banned terms, proper-name casing, a spelling standard, and mechanical rules like comma, number, and date style. It is the mechanical, checkable half of house style (the tonal half is Voice), expressed as structured data rather than prose. A lexicon is applied at compose as a wording transform only: it changes *how* a grounded claim is phrased, never *whether* something counts as a fact, and it adds nothing to the grounding record. It is deliberately not a tenth dimension; it rides the existing cascade at the workspace and recipe layers and contributes only to the artifact's identity.

### Rendering dimensions (how one finished piece is delivered)

- **Platform.** The rendering dimension for *where a piece gets published* — LinkedIn, Medium, a GitHub README, a personal site. A platform is a destination plus a constraint layer, chosen per deliverable (it is routing, never an instance-wide baseline). Its constraints come in two kinds: advisory norms, which ride the cascade and can be deviated from with a warning, and hard limits, which are enforced only at the fitting gate and can fit-or-block but never silently pass. Platform is the one dimension that projects values onto others — per-format advisories, fitting-strategy defaults, and a weak default output-type.
- **Language.** The rendering dimension for *which tongue* a deliverable is in. It is a thin registry whose entry id is simply the language tag, such as `en`. It is one of the three dimensions an instance must give a global default for, and it is part of a fitted variant's identity. Translation itself is a designed-but-deferred reconcile-time transform; the dimension ships now so the feature can drop in later without redesign.
- **Output-type.** The rendering dimension for *how a piece is serialized* — Markdown, HTML, PDF, docx, and so on. It is a pure serialization coordinate: it selects which Pandoc writer produces the bytes, and it is part of a deliverable's identity. It is one of the three dimensions an instance must give a global default for. The actual writer, engine, and pinned tool versions that realize an output-type live on a matching render-target entry.
- **Presentation.** The rendering dimension for *how a piece looks* — one entry is one brand's complete cross-target visual style (fonts, margins, templates, highlight style, and similar levers). It is applied deterministically at serialize time, on the already-produced document structure, in a single writer call with no expensive model step — which makes it the cheapest thing to change. It affects only the look, so it is part of a deliverable's identity but not the artifact's or the fitted variant's. Its built-in `plain` entry is the honest floor, so simply shipping the dimension changes no existing identity.
- **Render-target (not a dimension).** An entry in the render-target registry that *realizes* an output-type: it names the Pandoc writer to use, whether the bytes are produced in-system or handed off to an external renderer, and the pinned tool versions. By convention a render-target's id equals the output-type slug it serves, so dispatching is just "look up the target for this output-type." Switching a format between in-system and external rendering is a one-field edit here.

### Sources, grounding & confidence

- **Source (adapter and instance).** A read-only provider of grounding facts, in two layers. The *adapter* is the type — code that knows how to query a kind of source (a Graphify graph, a folder of documents) and declares its capabilities. The *source instance* is a bound configuration of that adapter: a specific connection, its characterization scores, and a content-kind tag. Sources are always read-only; the pipeline reads a client's graph by path and never writes to a client repo.
- **Content-kind (not a dimension).** A small registry that classifies *what a source's content is* — merged code, research papers, marketing copy — and carries a default bundle of scores for that class: how authoritative it is, how opinionated, its freshness policy, its review status. A source instance tags into one content-kind, inheriting those defaults, which can then be refined per fact at grounding time. It is the middle tier of source characterization, between the instance's own properties and the properties computed on each retrieved fact.
- **Grounding.** Reading facts out of a source and using them to back every claim a piece makes. Grounding is the system's central discipline: factual and technical statements must trace to facts actually extracted from a source, and every piece records the workspace, source repo, and source commit it drew from. Grounding happens first, before any writing; if a piece grounds to nothing usable, it blocks rather than inventing content.
- **Fact.** One claim retrieved from a source during grounding, carrying a confidence tier and a set of scores. Facts that clear the publish floor become the material the writer may assert; the rest are leads to verify. Every published claim keeps an inline reference back to the fact that backs it.
- **Grounding ledger.** The per-fact record kept inside a piece's intermediate representation: for each fact, its confidence tier, which source instance and repo and commit it came from, a traceability anchor, and a snapshot of its scores. The ledger is what lets reviews and citations resolve each claim back to its evidence. It stores ids, anchors, and commits only — never secret values.
- **Confidence tier (EXTRACTED / INFERRED / AMBIGUOUS) and the publish floor.** Every fact carries one of three tiers recording *how sure* it is: EXTRACTED (directly supported), INFERRED (reasoned but not directly stated), or AMBIGUOUS (uncertain). The publish floor is a hard framework invariant: only EXTRACTED-tier facts may be asserted as fact; INFERRED and AMBIGUOUS material are leads to verify, never published as fact. No configuration, run, or override can relax this floor, and later pipeline stages never promote a fact to a higher tier.
- **Traceability.** A separate, independent property of a fact answering *can you cite it* — whether it has a resolvable anchor such as a file-and-line, a commit hash, or a URL fragment. It is orthogonal to the confidence tier: a fact can be EXTRACTED yet un-anchored, or INFERRED yet cleanly anchored. The review stage checks citability independently of confidence.

### Selection, fanout & grouping

- **Selection (SelectionRequest).** The request that drives a run: a multi-select across the dimensions — one or more topics, personas, platforms, formats, and so on — plus global options. A selection is not one piece of content; it is an instruction that fans out into many. It is the single input shape shared by both interactive one-off runs and scheduled automations.
- **Fanout.** The expansion of a selection into concrete, individually-identified, idempotent work items. Content fanout crosses the content choices into distinct artifacts; rendering fanout crosses the rendering choices into many deliverables of one artifact. The one exception is the Goal dimension, whose multiple values stack into a single artifact instead of fanning out.
- **Recipe.** The per-artifact binding unit: a reusable bundle that binds exactly one entry per content dimension (topic, persona, format, voice) plus a goal-set and any configured values, and may also pin rendering targets. One recipe produces one artifact. A recipe is the L5 rung of the cascade, so it sets only the attributes it names; everything it leaves unset falls through to workspace, global, entry, and schema defaults. A selection fans out into many recipes.
- **Plan.** The deterministic, complete list of work items a selection resolves to, together with a hash of that list. The plan lets you see every item before any is run, and it organizes items into waves of mutually-independent units for safe parallel execution. Because it is deterministic, re-resolving the same selection at the same source commit yields the same plan and the same item ids.
- **Folio.** A pure purposeful set: an addressable, durable collection of *artifact references* with a stated purpose — and nothing more. A folio deliberately holds no dimension values, no platform or rendering intent, no ordering, and no schedule; it is orthogonal to all nine axes. It exists to group finished artifacts (for example, all the pieces of one campaign) so they can be found and worked with together, while any useful ordering is left to be computed by whoever consumes it.
- **Folio-type (not a dimension).** A framework-shippable blueprint that declares a typed folio's *member roles and structure* — for example a `repo-docs` folio with roles readme, getting-started, architecture. A folio-type names the shape of each intended member (which genre, which topic slot) as a recipe skeleton that the generating run fills in; it never carries concrete dimension values. It is consumed at generation time and then remains on the folio as declared structure for discovery and role-based ordering.
- **Workspace.** A per-client directory under `workspaces/` that holds everything specific to one client repo — its topics, sources, recipes, folios, artifacts, and deliverables. The workspace is the unit of client isolation: one client's content lives only under its workspace and can never leak into another's. There is one pipeline repo with many workspaces, never a separate repo per client, and a workspace name is a required input throughout the engine.

### Identity & the intermediate representation

- **Content-addressed identity.** The principle that a piece's identity is a hash of the inputs that produced it, not a name someone assigns. Because identity follows inputs, the same inputs always produce the same id, re-running an unchanged item is a no-op, and any real change produces a new id while the old one persists as history. This is what makes runs idempotent and every artifact traceable to exactly what it was built from.
- **Preimage.** The canonical, ordered bundle of inputs that an id is hashed from. For an artifact the preimage is the set of content coordinates and grounding pins, recorded so precisely that the id can be re-derived and verified. When an id is minted, a preimage check guards against collisions: if an id already exists with a different recorded preimage, minting fails loudly rather than silently reusing.
- **artifact-id.** The identity of a composed, platform-neutral piece — a hash of its content coordinates: topic, persona, format, voice, the sorted goal-set, the resolved source subset and source commit, and the delta of any tuned values against their floor (plus, when present, an outline digest or a lexicon). It keys the compose-once intermediate representation, it is the stable key a folio's membership refers to, and it is the idempotency key for composing: re-running an item whose artifact-id already exists does nothing.
- **fitted-id.** The identity of one artifact reshaped for a particular platform and language — the artifact-id plus those two coordinates. It names the reusable output of the fitting pass, so that one expensive fitting serves every output-type and presentation for that platform/language. It sits between the artifact-id and the deliverable-id, and it is a cache key rather than a separate kind of content.
- **deliverable-id.** The identity of one fully-rendered output — the fitted-id plus the output-type and the presentation. It keys the serialized bytes and is the idempotency key for rendering. Presentation lives only at this level (look is not content), which is why changing only the look produces a new deliverable without touching the artifact or the fitted variant.
- **Artifact vs. deliverable.** An *artifact* is the composed, platform-neutral piece — physically it *is* the canonical intermediate representation, keyed by artifact-id, produced once by the expensive writing step. A *deliverable* is one concrete rendered output of that artifact — a specific output-type and presentation for a specific platform and language, keyed by deliverable-id. One artifact yields many deliverables; the whole point of separating them is compose-once, render-many.
- **IR (intermediate representation).** The machine-generated document the system composes and then renders from: a JSON envelope with Markdown in its leaves and a grounding ledger attached. It exists in two persisted states — *IR-canonical* (platform-agnostic, one per artifact, the single source everything re-renders from) and *IR-fitted* (the output of the fitting pass, one per platform/language). Keeping content in this structured, platform-neutral form is what makes re-targeting to a new platform a re-fit rather than a re-write.
- **AST.** The Pandoc abstract syntax tree, in JSON — the deterministic pivot that every output passes through on its way to bytes. The system serializes the fitted IR into this one standard tree, always persists it, and then either renders bytes from it in-system or hands it to an external renderer. Because it is a standard interchange, a new output format is usually just one more target off the same tree, with no expensive model step.
- **Part (part-id).** An addressable sub-unit of a single artifact or deliverable, each with its own id and its own bytes, so a publisher can address, say, slide 3 directly. Parts come in two forms: composite parts, which a Format declares as named sub-outputs of one genre and which live stably in the IR; and reconcile-split parts, which the fitting pass produces when it splits one piece into a multi-part deliverable such as a thread or a carousel. A group of *separate* artifacts is a folio, not a part-split — the discriminator is simply how many artifact-ids underlie it.
- **Outline (the drive input).** A normalized planning scaffold that can steer how a piece is written. It has two distinct roles. On the *emit* path it is realized as its own ordinary artifact of the built-in `outline` genre — an editable outline you can render like any other piece. On the *drive* path it is a separate input attached to a normal artifact, entering the writer's prompt as a high-salience brief that outranks the dimensions for structure and emphasis. Either way it asserts no facts and adds nothing to the grounding record, so it opens no new fabrication vector; its normalized digest optionally joins the artifact's identity, and when absent it changes no existing id.
- **Generating-run (lineage).** The identity of one execution, stamped immutably on every artifact that run produced. Lineage is how "what did run X produce?" is answered — as a query by run id, source commit, or date — rather than by any container. It records provenance and history; an override's effect is captured here and in the id even though the override itself is never persisted.
- **SSOT (single source of truth).** The tracking spreadsheet, which is the sole authority for one thing only: status and progress. Any session-facing status document is a derived mirror of it, never an authority — if the two disagree, the spreadsheet wins. It is deliberately scoped: it owns the progress domain and nothing else about the content model.

### The pipeline stages

- **The two stages (ideation vs. generation).** At the product level the whole system is framed as two stages. *Ideation* turns a repo plus an audience into a ranked queue of content ideas; *generation* turns one chosen idea into a finished, formatted artifact. Ideation sits upstream and is intentionally left undesigned in the engine — it is product-plane work with no fixed contract — so everything the engine actually implements lives inside generation.
- **The two waves (compose vs. render).** Within generation the engine runs exactly two waves. Wave 0 is *compose*, keyed by artifact-id: it builds one platform-neutral artifact from grounded facts. Wave 1 is *render*, keyed by deliverable-id: it fits and serializes that artifact into concrete output files. The split is deliberate — the expensive, model-driven work happens once in compose, and the cheap, deterministic work happens many times in render.
- **Compose.** The first wave and the one expensive model step: the writer turns grounded facts into the canonical intermediate representation — a platform-neutral document with a grounding ledger — done exactly once per artifact-id. Compose is where content dimensions bind and where the publish floor is enforced on every claim. Its output is the single source that all rendering re-derives from.
- **Reconcile (fit).** The first render pass: a per-target model pass that reshapes one artifact's content to fit a specific platform and language — localizing, then reshaping toward the platform's capabilities and limits, then a terminal hard-limit gate that either fits the content or blocks, but never silently overflows. Its output is a persisted fitted variant keyed by fitted-id. It runs only when fitting is actually needed, and it is a cost boundary, not a lock: re-targeting to a new platform is always one more fit away, never a re-compose.
- **Serialize (render).** The second render pass: a deterministic, model-free transform that turns a fitted variant into the standard Pandoc tree and then into output bytes (or a hand-off payload for an external renderer). This pass — and only this pass — is truly free in the sense that the same inputs and the same pinned tools always produce identical output. Adding a new output-type or presentation to an existing tree is one writer call with no model step.
- **Review gates.** Two quality checks bracket the pipeline: an artifact review on the intermediate representation, run once and early before any fanout, and a deliverable review on every shipped output. The reviews re-check grounding — that claims carry evidence and that the evidence supports the claim — while the hard publish floor and tier-honesty are enforced earlier, at compose. Reviews surface concerns; they are part of how the system keeps published content tied to its sources.

## Requirements

Before a first run, put these in place:

- **The runtime toolchain.** The mission's dependency table names Homebrew... Node.js (current LTS)... Claude Code CLI... Python (current supported 3.x)... uv or pipx... Tailscale... n8n. The pinned Python dependencies live in the repo's pyproject.toml... uv.lock.
- **Pandoc for the render pass.** The serialize step is rendered by Pandoc, and Pandoc's binary version and AST api-version are pinned — a hard build requirement.
- **At least one bound source.** The pipeline reads client repos three ways; all read-only — a Graphify graph by path, an MCP query, or a wiki export. The matching readers live in pipeline/adapters/... folder.py, fsast.py, graphify.py, mock.py.
- **The Claude subscription transport.** Composition runs through Claude Code: the pipeline is a headless Claude Code CLI invocation authenticated on the Claude SUBSCRIPTION — never API keys, never ANTHROPIC_API_KEY.

## Setup

These steps take you from an empty checkout to one grounded artifact.

1. **Initialize the control-plane repo.** The bootstrap guide's B5 — optiquity-content-pipeline repo init step runs git init... git commit -m... # only on approval — the commit waits for your approval.
2. **Declare instance-global defaults.** Instance config lives under instance/ (defaults.template.yaml, defaults.yaml, ops/, profile.template.md); copy the profile template into place, as in cp instance/profile.template.md instance/profile.md. Voice, language, and output-type defaults are read as scope defaults by load_scope_defaults into a ScopeDefaults record.
3. **Create a workspace.** Each client gets an isolated workspace, made by copying the template: cp -R workspaces/workspace.template workspaces/self. The workspace name is a required argument throughout the engine — for example, CascadeEnv.__init__ takes a workspace parameter.
4. **Register a source pool.** Source definitions live in sources/; the engine turns registered entries into a pool with build_pool.
5. **Verify read-only grounding.** From the pipeline repo, confirm read-only grounding works with a smoke query — graphify query --graph <repo>/graphify-out/graph.json 'smoke test' returns grounded results.
6. **Invoke a recipe.** Recipes bundle a genre's settings; the shipped ones are in recipes/ (explainer-post.md, project-manual.md). Invoking one produces the first grounded artifact.

## Usage

The command-line surface is the launcher in scripts/... pipeline, dispatched by main. Its subcommands map to the tasks below.

- **Resolve a plan.** Ask for the parallel plan when you open a session: it is obtained via begin-session(want_parallel_plan = true) — no new verb. The plan lays out the two waves so you can see every work item before running any.
- **Generate an artifact.** Composition is wave 0, keyed by artifact-id, driven by continue-session{generate-next, only}: open the session, then call continue-session generate-next per item. Under the hood a thread runs run_thread, starting from a SelectionRequest; a ready-made one is available from demo_selection for a first run. The demo thread and MVP demo are wired as the subcommands _cmd_demo_thread and _cmd_mvp_demo.
- **Drive a genre with an authored outline.** To shape one artifact, attach an outline through the selection's outlines map; the request resolves it with outline_for, and the map is normalized by _normalize_outlines. The outline drives structure and emphasis without adding any new publishable fact.
- **Render and read the deliverable.** Rendering is the token-free wave 1, run by the _cmd_render subcommand (with _cmd_invoke for external hand-off). Output files are named by output_filename.
- **Operator subcommands.** Two round out the surface: an SSOT command _cmd_ssot and a drift-report command _cmd_drift_report.

## Internal design

A generation thread runs a fixed spine. The entry point is run_thread, which returns a ThreadResult and drives the per-item stages.

- **Ground.** Facts are gathered first. ground_item grounds one item and ground_batch a batch; the result is a GroundingOutcome that separates publishable_facts from leads. The driver refuses to proceed on an empty grounding via _grounding_abstain_check.
- **Resolve and bind the cascade.** resolve_compose resolves compose-time configuration and resolve_render the render-time configuration; each dimension is bound by _bind_dimension, folding layered values through _apply_rungs inside a CascadeEnv.
- **Compose.** The artifact stage runs _run_artifact, which calls compose_artifact. Compose builds the writer prompt with build_writer_prompt, parses the reply with parse_writer_output, and assembles the intermediate representation with _assemble_ir.
- **Render — reconcile and serialize.** The deliverable stage runs _run_deliverable, resolves render targets through resolve_render, and emits output through dispatch; multi-part outputs are addressed by split_part_addresses.
- **Persist.** Records are written by _persist and _persist_record.
- **Two review gates.** An artifact review runs via _run_artifact_review and a deliverable review via review_deliverable; their instructions live in pipeline/prompts/ (artifact_reviewer.md, deliverable_reviewer.md).

One limit shapes how deep this section can go: the facts available to this manual reach top-level definitions and one level of class methods, so call chains below that depth are not shown here.

## User-facing surface

The surface has four parts: the selection inputs, the verbs, the store, and the run-layer overrides.

- **Inputs.** A run is described by a SelectionRequest. Its axes expand into content coordinates via content_combinations and into render coordinates via render_coordinates.
- **Verbs.** The API modules live in pipeline/api/ (discovery.py, fetch.py, folio_verbs.py, invoke.py, manifest.py, render.py, results.py, session.py, token.py). The compose verbs are begin-session and its continue-session{generate-next, only}; the render side is the token-free render verb. External hand-off is carried by emit-manifest for side: external targets.
- **Store.** Persistent state is a WorkspaceStore, threaded through the engine — for example, _persist(doc, request, *, store: WorkspaceStore,...) writes into it.
- **Run-layer overrides.** Overrides bound at session start enter through CascadeEnv.__init__, which accepts an OverrideSet; individual values are ValueBindings parsed by parse_value_bindings.

## Extending it

Every extension point is a one-file change; a new axis/stage is a config addition plus its own registry directory, not a rewrite.

- **A new matrix value.** Drop a Markdown entry into the axis directory — topics/, personas/, platforms/, or formats/ — and the resolver picks it up.
- **A recipe.** Add a file under recipes/ to bundle a genre's settings.
- **A source adapter.** Add a reader module under pipeline/adapters/ next to folder.py, fsast.py, and graphify.py, then register it so the driver can select it.
- **A scope default.** Set instance- or workspace-level defaults that load_scope_defaults reads into a ScopeDefaults.
- **A whole pipeline stage.** Adding an editor-style stage is three steps: Add the agent file... Register it in the pipeline stage list (config), positioned after writer... items flow through the new stage and record its result column. New stages attach here without disturbing existing ones.

## Known issues and open items

Some things are deliberately deferred; treat the tracker as the authority, not this manual.

- **The known-issues tracker.** docs/ carries known-issues.md, the register that named deferrals point to.
- **Reserved and deferred features.** The design's reservation table defers a range of features — Language/localization fanout GA... AIMD width auto-tune... Per-part dimension overrides... HTTP shim for cloud orchestrators among them — each designed to slot in additively later.
- **Unverified transport.** The invocation details are not yet proven: the transport's specifics are unverified and gated before build, including subscription-auth headless operation and the n8n→headless mechanism.
- **Maintainer-gated runs.** Actions that cost or commit are held for a maintainer. The bootstrap commit runs only on approval, and a session should update state.md and propose (not make) a commit.
- **Presentation-asset lowering on the production path.** This manual has no grounded fact fixing whether presentation-asset lowering runs on the production path, so it stays a lead to verify in the known-issues tracker rather than a claim stated here.
