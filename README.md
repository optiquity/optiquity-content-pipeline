# Optiquity Content Pipeline

## What it is

The Optiquity Content Pipeline is an open-source **framework** for turning your own repositories into targeted content — documentation and marketing alike — that stays tied to a source of truth. It is a control plane: **content-free by design**, it ships the machinery and generic defaults while you supply the audiences, platforms, formats, and workspaces. Its mission document frames it as a repo-grounded, extensible, two-stage pipeline — ideation (repo + audience → ranked idea queue) and generation (idea → formatted artifact) — running on Claude Code CLI, grounded in read-only Graphify knowledge graphs of source repos. Grounding is the core idea: Graphify turns any folder (code/docs/scripts/PDF/images) into a queryable knowledge graph, and the pipeline reads that graph to back every claim it makes.

The read-only boundary is firm. The pipeline reads source graphs (by file path, MCP query, or pre-exported wiki) and only ever writes inside optiquity-content-pipeline/. Client repositories stay untouched — each one is checked out locally, and its graph is built in place, where the graphify-out/ is gitignored inside the client repo, so it never dirties it.

Drafts themselves are generated by a chain of Claude Code agents — a **researcher → writer → reviewer** — the product-plane layer that produces and checks each piece within the same CLI.

For this README the bound sources are the pipeline's own tree: its design record and its Python engine. It is written for the person standing the project up and keeping it running — what the design calls the Primary author (solo/small-team).

## What it does

At the product level the pipeline is designed around two stages. **Ideation** — reading a source repo's knowledge graph together with your target audiences to propose a ranked queue of ideas worth writing — is the intended first stage but is **not built in v1** (you hand-author the topics; see *Known limitations*). **Generation** — turning one chosen topic into finished, formatted artifacts — is what the engine does today.

Generation is where the engine does its work. You give it a selection across the matrix's nine axes — topics, personas, formats, voices, and goals shape the substance; platforms, languages, output-types, and presentations package and route it — and it fans that out into many concrete, individually-tracked items, one per combination. Each item is *grounded* first (facts pulled from the source graph; it blocks rather than invent if nothing usable grounds), *composed* once into a platform-neutral artifact, and then *rendered* into as many outputs as you asked for. Because that one artifact is composed once and rendered many times, re-targeting a piece to a new platform is a re-fit, not a re-write; and because every claim traces back to a graph fact carrying a confidence tier, only directly-supported facts are ever stated as fact.

You drive all of this from a friendly local CLI — `preview`, `generate`, `recipe`, `entry`, `list`, and more (the complete command + flag reference is [`docs/reference/cli.md`](docs/reference/cli.md)) — that is **dry-run by default**: it prints the whole plan and the exact count of paid pieces, and spends nothing until you add `--go`.

By default the pipeline runs on your **Claude subscription** (flat-rate). You can also assign an **API key** — single- or multi-tenant — per scope (global, user, zone, or workspace), bounded by a **hard weekly dollar cap** plus one install-wide umbrella, so a run reserves its worst-case cost against the cap *before* it spends and refuses if it would exceed it. Keys live outside the repo (`$OPTIQUITY_SECRETS_DIR`), referenced by handle, never in a command line. Full setup is in [Transport](docs/transport.md).

## Who it's for

This README is written for the person standing the project up and keeping it running — the design's *Primary author*, a solo operator or small team.

It also frames two overlapping audiences drawn from the two-repo operating model (`docs/operating-model.md`): **framework maintainers**, who keep the public, content-free framework and share improvements upstream; and **instance operators** — you, and any other user — who clone that framework into a *private instance* and build their own content pipeline on top, pulling framework updates non-destructively because framework files and instance content never share a file. Your own instance is simply the first private instance; there is always one pipeline repo with many client workspaces, never a repo per client.

## Known limitations

A few things are deliberately deferred in v1 — the full, authoritative list lives in [Extending it → Known issues](docs/guide/extending.md#known-issues-and-open-items), which points to the running tracker in `docs/known-issues.md`. In short:

- **Ideation is not built yet (GAP-7).** The system generates content *for* a topic across the whole matrix, but it cannot yet discover or rank *what* to write about — you hand-author each topic. That is half of the intended two-stage design.
- **`recipe`/`select` don't take a zone yet (GAP-13).** They author into the `default` zone regardless of `--zone`, so a workspace living only in a non-default zone would get an orphaned `default`-zone path. The near-term fix mirrors the `entry --zone` change.
- **The HTTP shim has honest edges.** Composing in a single HTTP call is not wired — the supported path is two calls (`begin-session{generate!=none}` is still a `501` placeholder); the concurrency cap is advisory; and one DNS-rebinding edge is mitigated, not fully closed.
- **The API-key transport has documented residuals.** `--user`/`--zone` are addressing, not authentication (the guarantee is a bounded blast radius via the caps, not authenticated identity); a local delete of the spend meter reopens the cap; and it assumes a single writer host — see *Residual risks* in [Transport](docs/transport.md).
- **Several features are reserved for later** — language/localization fanout (the `languages` axis exists but the localize step is a deferred slot), per-part dimension overrides, and others — each designed to slot in additively.

Treat the tracker, not this summary, as the authority.

## Two ways to run it

Before the concepts, it helps to know how you would actually run the framework. There are two operating models — both covered in `docs/operating-model.md`, both with a QuickStart section.

- **Solo.** Clone the repo, add a workspace, and run it on your own repos. This is the fastest path; `quickstart.md` §A walks it end to end. (Your own repo is a client too — by convention you are `users/<you>/zones/default/workspaces/self`.)
- **Framework + private instances.** You maintain this public framework repo, and each user — including you — keeps a *private instance* that pulls your framework improvements non-destructively via `scripts/update-from-upstream.sh`. Because framework files and instance content never share a file, those updates merge cleanly and leave your content untouched, while the public repo stays content-free (enforced in CI, not by willpower). `quickstart.md` §B covers the maintainer setup.

Your own instance is simply the first private instance; others clone the public repo to make their own. Either way there is only ever one pipeline repo with many workspaces — never a separate repo per client.

However you deploy it, there are two doors onto the same operations. Locally you drive the pipeline through the command line (`scripts/pipeline`). A cloud-hosted automation tool that cannot reach your command line — n8n Cloud, Make, Zapier, Google — drives it instead over HTTP, through the `pipeline serve` shim, behind a login. Both doors run the identical verbs; the HTTP door is described under *HTTP access* in the [Interfaces guide](docs/guide/interfaces.md#http-access-cloud-orchestrators).

## Durable rules

Five invariants hold across every session and every instance, and the rest of this README assumes them. They are stated in full in `CLAUDE.md` and elaborated throughout the [glossary](docs/guide/concepts.md#glossary) — this is the short authoritative summary.

1. **Read-only, always.** Source and client repos are never written, edited, moved, or committed to. The pipeline only reads a client's Graphify graph by path.
2. **A workspace per client — never a repo per client.** Each client repo gets one `users/<user>/zones/<zone>/workspaces/<workspace>/` directory (the `users/<user>/` and `zones/<zone>/` segments are both isolation/addressing prefixes — a **zone** groups a user's workspaces and defaults to `default`); there is one pipeline repo with many workspaces, and one client's content can never leak into another's. Same-named workspaces in different zones are distinct, store-isolated workspaces.
3. **The tracking spreadsheet is the single source of truth** for status and progress. `state.md` is a derived mirror of it — if they disagree, the spreadsheet wins and `state.md` is updated to match, never the reverse.
4. **The public framework repo stays empty of client content.** Generic `provenance: framework` defaults are welcome (they are the deliverable); an instance profile, any `provenance: instance` entry, and real client workspaces never appear there.
5. **Instances extend by adding files; they never edit framework files.** Downstream adds populated registries, workspaces, and a profile; framework improvements come from upstream, so updates stay conflict-free.
